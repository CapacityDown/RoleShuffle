# 全役職の運用リスク確認

確認日: 2026-09-30

対象: RoleShuffle v4.5.3 build502 / `4360ef891fe56f332ab13db6ab25fdf730609612`

対象数: 通常41役職＋隠し2役職、計43役職

## 結論

優先して対応・判断する項目は6件です。特に、Tunaの低速移動判定、MageのHP消費、Bodyguardの肩代わりは、プレイヤーが説明どおりに行動しても死亡につながる条件を確認しました。

確認方法は現行ソースの点検、実際の処理を抜き出したシミュレーション、既存の自動チェック、インストール済みゲームとの照合です。実際のマルチプレイでの再現確認は未実施です。「新たな重大指摘なし」は、この確認範囲での結果であり、あらゆる状況での安全を保証する意味ではありません。

今回の確認に伴う変更は、監査記録・再現用ツール・既存検証ツールの修正です。ゲームの仕様、設定、配布DLL、RSO_TESTはbuild502のままです。

## 優先項目

### A1: Tunaが移動中でも静止扱いになる【高・シミュレーションで確認】

- 低速で移動している場合、フレームレートによって移動と認められなくなります。
- 毎秒0.5mで4秒間移動する同じ条件でも、60fpsでは無傷、120fps・240fpsでは120 HPから110 HPへ減少しました。ステージ開始時の猶予終了後の条件です。
- 重い物を押す、位置を微調整する、低速で逃げる場面で、「動いているのに死ぬ」原因になります。
- 推奨対応: 一定時間内の移動距離で判定し、フレームレートの違いで結果が変わらないようにする。
- 根拠: [移動判定](../../StageRoleController.cs#L1413)。同じ処理を使った再現結果は後述。

### A2: Mageの「消費で死亡する詠唱は拒否」が通信遅延時に成立しない【高・条件付き、シミュレーションで確認】

- HPの支払いが反映される前に次の詠唱が受理されると、残りHPを超えて支払えます。
- HP15、消費10、クールダウン0.1秒、0.2秒間隔で2回詠唱する条件で、遅延なしでは2回目が拒否されHP5、反映が遅れた場合は2回とも受理されHP0でした。
- 既定のクールダウンは3秒です。上の再現は短縮設定を使っています。既定値でも長い通信停止や、ホストへまだ伝わっていない被弾がある場合の完全な死亡防止は保証できません。
- 推奨対応: まだ反映されていない支払いを差し引いて受付を判断する。同時被弾も含めた死亡防止については、未導入参加者で成立する範囲を明確にする。
- 根拠: [詠唱受付とHP消費](../../MageRoleRuntime.cs#L97)、[HP消費の実行](../../MageRoleRuntime.cs#L276)。

### A3: Bodyguardの「HPを1残す」が通信遅延時に成立しない【高・条件付き、シミュレーションで確認】

- Bodyguard本人への攻撃がまだホストへ反映されていない間に肩代わりすると、実際の残りHPを超える量を引き受けます。
- ホストが認識するHP30、本人は直前の被弾でHP5、味方の40ダメージを50%肩代わりする条件では、20ダメージを受けて死亡しました。
- また、短時間に複数の攻撃が重なり原因を特定できない場合、肩代わり自体を見送る処理があります。「範囲内にいれば常に半減する」とは扱えません。
- 推奨対応: 遅延・連続被弾時の保護方式を見直す。保証できる条件に合わせて説明も改める。
- 根拠: [肩代わり量](../../EventRoleRuntime.cs#L443)、[複数攻撃時の見送り](../../EventRoleRuntime.cs#L388)、[肩代わり実行](../../EventRoleRuntime.cs#L923)。

### A4: Mage / Tricksterの表情による誤発動【高・既知の制約を再確認】

- ホストのみ導入の参加者では、メニューを閉じたときに元の表情へ戻る動作を、能力発動の操作と区別できない場合があります。
- MageではHP消費と攻撃、Tricksterでは敵を引き寄せるデコイの設置につながります。味方の近くや退避中のメニュー操作で事故になる可能性があります。
- これはREADMEにも記載されている制約です。ホスト自身のメニュー復帰、表情の解除、他人の表情操作の偽装を除外する処理と検証はあります。
- 当面の運用: 誤発動を避けたい場合は該当する表情の設定を`Disabled`にし、チャットによる発動を使う。
- 根拠: [表情の受付](../../RoleExpressionPatches.cs#L53)、[表情の既存チェック](../../tools/ExpressionChecks/Program.cs)、[公開説明](../../package/README.md)。

### A5: Tunaには蘇生後専用の猶予がない【高・仕様上の危険、シミュレーションで確認】

- ステージ開始時の5秒間の猶予は、蘇生で付け直されません。通常の静止判定だけが再開します。
- 既定値は静止3秒後から0.1秒ごとに1ダメージです。HP1で蘇生し、その場に留まると約3.1秒後に再死亡する条件を確認しました。
- トラック内を除外する処理もありません。メニュー操作中、周囲の安全確認中、動けない状態での蘇生に注意が必要です。
- Courierのbuild502で導入済みの蘇生猶予とは別の問題です。
- 推奨対応: 蘇生後の短い猶予を設け、実際に操作を再開できる時点と合わせる。静止ダメージ自体は役職本来の制約として扱う。
- 根拠: [静止ダメージ](../../StageRoleController.cs#L1413)、[死亡時の処理](../../StageRoleController.cs#L1915)。

### A6: Tricksterの設置直後に感染すると、旧役職のデコイが残り得る【中・ソースで条件を確認、実機未確認】

- デコイの設置開始から準備完了までの間にInfluenzaへ変わると、取り消しが間に合わず、その後でデコイが有効になります。
- すでに動いているデコイを消す処理はありますが、準備中の設置を取り消す処理が不足しています。
- 結果として、役職を失った後も旧デコイが敵を引き寄せる条件が残っています。既定の持続は25秒です。
- 推奨対応: 感染・離脱時に準備中の設置も取り消し、設置完了時にも役職と本人の状態を確認する。
- 根拠: [感染時の処理](../../InfluenzaRuntime.cs#L139)、[個人のデコイ削除](../../TricksterRoleRuntime.cs#L163)、[設置完了](../../TricksterRoleRuntime.cs#L224)、[稼働中だけを消す処理](../../TricksterRoleRuntime.cs#L278)。

## 補足: テスト操作・設定での注意

- ステージ中のテスト用役職変更は、変更対象外も含めた能力の再初期化を伴います。Mechanic / Electricianの使用済み量が戻り、Mageの発射物・Tricksterのデコイ等が消えるため、通常プレイの残量検証と混ぜないことを推奨します。根拠: [役職変更](../../StageRoleController.cs#L822)、[修理・充電の初期化](../../UtilityRoleRuntime.cs#L49)。
- Phoenixの蘇生遅延と、ステージ失敗を待つ時間は別設定です。短すぎる待機時間では、Death Headの準備や蘇生が終わるまで待てない場合があります。既定は蘇生遅延2秒・失敗待機5秒です。
- Influenzaの感染は通常の抽選とは別に役職を置き換えます。抽選で設定した支援役の人数や危険役の人数が、感染後も維持されるとは限りません。
- アップグレードアイテムの保持は既定OFF。ONでもLifter・Rammerの固定項目やInfluenzaの最大HP制約が優先されます。使用した直後の見た目だけで保持失敗と判断しないでください。

実際の`TickTuna`、Mageの詠唱受付・消費、Bodyguardの肩代わり・支払い処理を変更せずに抜き出して実行しました。位置、時間、HPの通知遅延、攻撃の生成は模擬しています。Unityの物理や実際の通信を再現したものではありません。

|---|---|
| Tuna / 0.5m毎秒 / 4秒 / 60fps | 120 HP → 120 HP |
| Tuna / 0.5m毎秒 / 4秒 / 120fps | 120 HP → 110 HP |
| Tuna / 0.5m毎秒 / 4秒 / 240fps | 120 HP → 110 HP |
| Tuna / 開始猶予後 / 1 HP蘇生 / 静止 | 約3.1秒後に死亡 |
